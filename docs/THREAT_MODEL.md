# CapMint — Threat Model

> **Purpose.** State plainly which attacks CapMint *prevents*, which it only *detects*, and which it
> does not address at all. Written because "anti-counterfeiting" conflates several unrelated attacks,
> and sizing a finding wrongly is as costly as missing it.
>
> **Before assigning severity to any finding, ask the actor question: *who can actually do this, and
> who is authorized to assert it?*** Code-level reasoning tells you what the system does. It never
> tells you whether it matters. See `AGENTS.md` §5.

Companion docs: `SCOPE_BOUNDARY.md` (what CapMint is and is not), `REAL_WORLD_READINESS.md` (launch
gate), `ORGANIC_PIPELINE.md` (where CapMint sits in the farm→consumer chain).

---

## Ground truth: codes cannot be guessed

Verified in `backend/mint-service/src/index.ts`:

- The QR encodes `verificationUrl`, which carries a `public_identifier` generated by
  `crypto.randomUUID()` — a v4 UUID, 122 bits of entropy.
- `serial` is `generateSerial(12)` over a 36-character alphabet using `crypto.randomBytes` —
  36¹² ≈ 4.7 × 10¹⁸.

Both are cryptographically random. **Enumeration and guessing are not viable attacks.** An attacker
cannot invent a valid code; they must obtain a real one. Every attack below is a variation on *how*
they obtain it, or on the producer issuing too many in the first place.

## Attack A — Over-issuance by the producer  ✅ **PREVENTED**

A producer certified for 10,000 kg mints unit codes for 30,000 kg and sells conventional product as
organic. **Every code is genuine and verifies perfectly**, so scanning proves nothing and no party
downstream can detect it.

The attacker is the system's own customer. This is the attack CapMint exists to stop, and the one
competitors do not address — Acviss and similar vendors solve Attack B.

**Controls:**
- `reserveLotIssuance` / `reserveBudgetCapacity` (`packages/shared/capacity.js`) gate every mint path,
  including `/verify/register`. Both recompute usage from **actual rows** (`COUNT(*) FROM unit_codes`)
  rather than a stored counter, so the ceiling holds under retries — retry-safe by construction.
- `verifyBudgetAuthority` is fail-closed: non-string/empty signature, missing certifier key, or any
  exception returns `false`.
- DB backstop: `chk_budgets_remaining CHECK (consumed_quantity <= approved_quantity)`.
- Capacity originates from a **certifier-signed** budget. A producer cannot self-issue quota: the
  signature is written only by certifier activation (PR #12; `budgets.signature_bundle` is NULL until
  then, migration 0022).

**Residual risk:** the certifier is trusted. A corrupt or compromised certifier can authorize a budget
larger than the real harvest. CapMint proves *a certifier authorized this quantity*, not *this
quantity was grown*. Detecting certifier fraud requires cross-checking against NPOP/TraceNet
land-area and yield data — not currently implemented.

## Attack B — QR cloning by an outsider  ⚠️ **DETECTED ONLY, NOT PREVENTED**

A counterfeiter buys one genuine jar, photographs its QR, and reprints it on thousands of fakes.

**Software cannot prevent this, and no amount of cryptography changes it.** A QR is a number; a
photograph of a number is a perfect copy. The attacker breaks nothing — they photocopy. Any claim
that a purely digital system "stops counterfeit QRs" is false.

**What CapMint does instead — detect after the fact:**
- Geovelocity: consecutive scans implying travel faster than **800 km/h** set `clone_flag` on the unit
  code and raise the `CLONE-SUSPECT` verdict (`backend/verification-service/src/index.ts`).

**Limits, stated honestly:**
- Detection requires *someone to scan both jars*. A cloned batch sold entirely within one city may
  never trip the threshold.
- Detection is **after** the fake has been sold. The consumer holding the counterfeit is already
  harmed.
- The first scan of a cloned code is indistinguishable from a genuine first scan.

**Prevention requires a physical layer**, tracked in the backlog and deferred until a paying customer:
- **Copy-detection patterns (CDP)** — microscopic print detail lost on reproduction. Zero consumer
  effort. Honest limit: strong against ordinary photocopy fraud, but an ML-equipped attacker can push
  false accepts to 26–51% (Chaban et al., IEEE WIFS 2021). Not a silver bullet.
- **Two-code / tag-couple** — a visible QR plus a hidden code under a tamper-evident seal. A fraudster
  photographing a shelf never sees the hidden code.

Both cost money per unit and require packaging changes.

## Attack C — Code leakage before labelling  ⚠️ **PARTIALLY DETECTED**

Codes are minted digitally before certification, and the physical label is attached only *after*
certification (`SCOPE_BOUNDARY.md`). Between those two moments, valid codes exist in the database and
at the print vendor but are on no jar.

An insider at the printing partner, or anyone with database or API access, can take that list and
print labels **before** the genuine ones are attached. The fakes carry real codes and may reach shelves
first.

This attack points at your own supply chain rather than an anonymous copier, which makes it both rarer
and more serious when it occurs.

**Current state:** geovelocity still fires, but the *scan log* loses the evidence. Verdict priority
ranks `NOT_CERTIFIED` above `CLONE-SUSPECT`, so a pre-label clone persists as `NOT_CERTIFIED` in
`scan_events`. `unit_codes.clone_flag` and the API's `cloneSuspect` / `risk` fields still carry the
signal, so the alarm fires — but an investigator querying scan history will not find the case.

**Open — HO-028.** Record the anomaly in the existing unused `scan_events.anomaly_flags` column while
keeping the consumer-facing verdict calm. No migration required.

---

## Attack D — Dishonest verification output  ✅ **CLOSED**

The system asserting more than it knows: showing a consumer an organic certification that does not
exist. Not an external attacker, but it destroys the credibility everything else depends on.

Closed by PRs #10 and #11 — the verdict now consults real certification state (`NOT_CERTIFIED`,
migration 0021), and fabricated NPOP/NABL credentials, invented provenance, fake GPS fed into the
clone detector, and an unauthenticated login bypass were all removed. Guarded by
`backend/e2e-tests/test/verification-honesty.test.ts`.

## Summary

| Attack | Actor | Codes | Status |
|---|---|---|---|
| **A** — over-issuance | the producer | genuine | ✅ prevented |
| **B** — QR cloning | outside counterfeiter | genuine, duplicated | ⚠️ detected only; prevention needs a physical layer |
| **C** — pre-label leakage | printer / insider | genuine, not yet attached | ⚠️ alarm fires, audit trail incomplete (HO-028) |
| **D** — dishonest output | the system itself | n/a | ✅ closed |

**Positioning consequence.** CapMint is a **supply-integrity** product, not a consumer
anti-counterfeiting product. The defensible claim to a buyer is *"this producer cannot sell more than
they were certified to grow."* Pitching it as "stops counterfeit QRs" invites a direct comparison with
Acviss, which attacks B and wins.
